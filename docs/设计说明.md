## 3. 结构模型

### 3.1 两种主体

| 主体 | 标识 | 在树上 | 能力 |
|---|---|---|---|
| 成员（agent） | `m_` + 6 hex | ✓ | 全部 |
| 人 | `h_` + 6 hex | ✗ | 读全部会话、读组织图、往群发言、发指令 |

两者都有 token，走同一套认证、同一套接口。**"人"是一张独立的表**：没有父、没有状态机、没有子组织。

### 3.2 树

一条边 `parent_id`。约束：

- 恰好一个成员 `parent_id IS NULL`（根），由唯一索引保证
- 根不能被删除（§8.2）
- **活子组织** = 自己 + 递归的后代，**`gone` 的不计入**（用于 §3.3 与可见性）
- **曾属子组织** = 自己 + 递归的后代，**包含 `gone`**（仅用于删除幂等与职责追溯，§8.2）

两个概念要分开：群和可见性只认活子组织；删过一次再删一次要能认出来，所以幂等判定沿 `parent_id` 链走，不看状态。

### 3.3 群的存在条件

```
children(m) = { c : c.parent_id = m ∧ c.status ≠ 'gone' }
群(m) 存在   ⟺  children(m) ≠ ∅
群(m)        =  {m} ∪ children(m)
```

- 叶子没有群，平台不准备空群
- 子成员全部消失后群随之消失；它的历史仍可读，但不能再往里发
- 每个成员最多属于两个群
- **群不是一张表**，是 `parent_id` 的一个查询

### 3.4 `to` 的两套形态

写侧（`POST /v1/messages`、`POST /v1/control`）用"发给谁"：

| 写法 | 含义 |
|---|---|
| `"g:<o>"` | 发到群(o) |
| `"<m>"` | 发给成员 m（一对一）|

读侧（`GET /v1/messages`）、gap 的 `to`、`conversations` 的 `to` 用**会话 id**：

| 会话 | id |
|---|---|
| 群 | `g:<o>` |
| 一对一 | `dm:<min(a,b)>_<max(a,b)>` |

`GET /v1/messages` 的 `to` 两种都接受：给 `dm:` 形式直接用；给裸成员 id 就按"我和他的一对一"派生；给 `g:` 形式直接用。

一对一不需要创建：会话 id 是两个身份的纯函数，首次发消息时惰性出现。会话内序号**永不回收**——群消失后 `conversation_seqs` 的行也不删，重建同名群继续往上加，这样旧消息里的编号永远指同一件事。

### 3.5 结构规则（这不是权限）

本设计没有权限系统，只有结构后果。全部规则如下：

| 动作 | 成立条件 |
|---|---|
| 读 / 写 群 `g:o` | 我是 `o` 或 `o` 的直接子成员（§3.3 `children(o)`）；或我是人 |
| 读 一对一 `a_b` | 我是 a 或 b，或我是人 |
| 写 一对一 | 我是 a 或 b（人不能）|
| 往任意成员发一对一 | 我是 `alive` 的成员，对方是 `alive` 的成员 |
| 发指令 | 我和每个目标同群（父/子/同父兄弟）；我是人则可发给任何成员 |
| 创建子成员 | 我是 `alive` 的成员（不计数量、不计层数）|
| 删除 | 目标在**曾属子组织**内（含我自己）；根除外 |
| 重发 token | 目标是我的**直接子成员**（创建者）|
| 读组织图 | 任何主体 |
| `poll` | 成员 |

三点说明：

1. **"子组织内"是结构作用域，不是权限**。它替代的是"我是它的上级"这个说法。
2. **人只能看和说**：不能创建成员、不能删成员、不能重发 token、没有一对一。人可以发指令、可以查自己发出的指令。
3. **群消失后**，所有者仍可读历史（通用规则已覆盖），但不能再发——没有收件人。

### 3.6 两套投递

| | 消息 | 指令 / 通知 |
|---|---|---|
| 载体 | `messages` + `inbox` | `controls` + `control_receipts` |
| 送达方式 | `poll` 取走即消费 | `poll` 取走即 delivered |
| 状态 | 内部消费指针 `member_cursors.last_seq` | 每收件人 `pending` / `delivered` |
| 人的情况 | 不写 inbox，只读 | 不作收件人；可发、可查自己发的 |

两者共用一次 `poll`，各自独立结算：一条消息处理失败只影响消息指针，不会挡住一条终止通知。

## 4. 数据模型

SQLite（WAL）。时间戳一律 **Unix 毫秒**。

```sql
members(
  id            TEXT PRIMARY KEY,     -- 'm_' + 6 hex
  name          TEXT NOT NULL,        -- 创建时确定，永不改动
  parent_id     TEXT REFERENCES members(id),   -- 根为 NULL
  is_root       INTEGER NOT NULL DEFAULT 0,
  status        TEXT NOT NULL,        -- 'alive' | 'gone'
  token_hash    TEXT NOT NULL,
  request_id    TEXT,                 -- 创建幂等键
  created_at    INTEGER NOT NULL,
  last_seen_at  INTEGER,              -- 最近一次鉴权成功的请求（§9）
  heartbeat_at  INTEGER,              -- 最近一次心跳；NULL = 从未跳过（§9.1）
  gone_at       INTEGER,
  gone_reason   TEXT
);
-- 名字全表唯一，包括已删除的：删掉的成员的旧消息里那个名字不能被别人占用
CREATE UNIQUE INDEX ux_member_name ON members(name);
CREATE UNIQUE INDEX ux_root        ON members(is_root) WHERE is_root = 1;
CREATE UNIQUE INDEX ux_spawn_idem  ON members(parent_id, request_id) WHERE request_id IS NOT NULL;

humans(
  id            TEXT PRIMARY KEY,     -- 'h_' + 6 hex
  name          TEXT NOT NULL UNIQUE,
  token_hash    TEXT NOT NULL,
  created_at    INTEGER NOT NULL,
  last_seen_at  INTEGER
);

conversation_seqs(conv_id TEXT PRIMARY KEY, last_seq INTEGER NOT NULL DEFAULT 0);
  -- 会话内序号分配器；群消失后这一行也不删

messages(
  conv_id       TEXT NOT NULL,
  seq           INTEGER NOT NULL,     -- 会话内 1..N，永不回收
  sender_id     TEXT NOT NULL,        -- 成员 id 或人的 id
  sender_kind   TEXT NOT NULL,        -- 'member' | 'human'
  client_msg_id TEXT,
  body          TEXT NOT NULL,        -- ≤ 64 KiB
  meta_json     TEXT,                 -- ≤ 4 KiB
  created_at    INTEGER NOT NULL,
  PRIMARY KEY (conv_id, seq)
);
CREATE UNIQUE INDEX ux_msg_idem ON messages(sender_id, client_msg_id)
  WHERE client_msg_id IS NOT NULL;

mentions(conv_id TEXT, msg_seq INTEGER, member_id TEXT,
         PRIMARY KEY (conv_id, msg_seq, member_id));

inbox(                                -- 消息投递快照，只有成员有
  seq           INTEGER PRIMARY KEY AUTOINCREMENT,  -- 全局自增，保证同一成员内单调；不对外暴露
  member_id     TEXT NOT NULL,
  conv_id       TEXT NOT NULL,
  msg_seq       INTEGER NOT NULL,
  created_at    INTEGER NOT NULL
);
CREATE INDEX ix_inbox_member ON inbox(member_id, seq);

member_cursors(member_id TEXT PRIMARY KEY, last_seq INTEGER NOT NULL DEFAULT 0);

controls(
  seq           INTEGER PRIMARY KEY AUTOINCREMENT,   -- 全局指令号
  id            TEXT NOT NULL,        -- 发送方幂等键
  from_id       TEXT NOT NULL,        -- 'sys' / 成员 id / 人的 id
  to_json       TEXT NOT NULL,        -- 原样保存请求里的 to 的 JSON（单个 id / 数组 / "g:<o>"）
  cmd           TEXT NOT NULL,        -- 自由一行文本，1–200 字符，不解释内容
  payload_json  TEXT,                 -- 不透明，≤ 64 KiB
  reply_to      TEXT,                 -- 发送方自定义的关联 id，平台原样透传
  created_at    INTEGER NOT NULL,
  UNIQUE(from_id, id),
  CHECK (length(cmd) BETWEEN 1 AND 200)
);

control_receipts(                     -- 收件人在展开时才确定
  control_seq   INTEGER NOT NULL,
  to_id         TEXT NOT NULL,
  state         TEXT NOT NULL,        -- 'pending' | 'delivered'
  delivered_at  INTEGER,
  PRIMARY KEY (control_seq, to_id)
);
CREATE INDEX ix_receipts_pending ON control_receipts(to_id, state);

meta(                                 -- 平台身份与启动观测
  key           TEXT PRIMARY KEY,
  value         TEXT NOT NULL
);
```

`meta` 有三行，值都是字符串：

| key | 含义 |
|---|---|
| `platform_id` | 平台身份，自动生成时形如 `p_` + 8 hex；建库时写一次，之后以库里的值为准（目录名与它不一致时拒绝启动，见下）。显式给的 id 原样使用，形状不受这条约束，但必须是单个目录名。旧库被接纳时按接纳后的目录名补写 |
| `created_at` | 这个库第一次被打开的时间（Unix 毫秒）。**0.2.0 的旧库没有这个值**，第一次被 0.3.0 打开时补写——所以对旧库它记的是"被 0.3.0 接管的时间"，不是建库时间；真实建库时间在旧库里无处可寻 |
| `server_version` | 最后一次打开/写过这份数据的程序版本；每次启动用 `SERVER_VERSION` 覆盖，是观测值，不参与任何判断 |

`platform_id` 不跟随目录改名。目录名与库里的值不一致时，打开数据库不会覆盖它；如果调用方显式要求了另一个 id（`options.platformId` / `PIGROUPS_PLATFORM_ID`），报错并在错误里同时给出两个 id——这是打开了另一个平台的库，不是顺便改名。**`main.ts` 每次启动都把目录名当显式 id 传进来**，所以对 CLI 而言这条意味着：把库搬到新目录名下面 = 拒绝启动。身份以库为准，目录必须跟着身份，反过来不行，所以错误里的建议是"把目录名改回 `<库里的 id>`"，不是"用库里的 id 再起一个"——后者会新建一个空平台，把数据变成永久的歧义。

这个检查发生在任何写入之前：一次被拒绝的打开不会给别的平台的库留下 `-wal`、表结构或 `meta` 行。

`meta` 不是版本表；它只记录平台身份和这个观测值。

**没有的表**：`groups`（§3.3 算出来）、`conversations`（id 是纯函数）、人的消费指针（人的浏览位置属于客户端）、任何文件相关表。

## 5. 消息

### 5.1 发送

```
POST /v1/messages { to, body, mentions?, meta?, client_msg_id? }
```

一个事务内：检查群是否存在 → 分配会话内 `seq` → 写 `messages` → 写 `mentions` → 给每个收件人写一行 `inbox`。

```
to = 'g:<o>'
  群(o) 必须存在（children(o) ≠ ∅），否则 404 no_such_group
  发送者必须是 o 或 o 的直接子成员，或是人
  收件人 = 群(o) \ {sender}，去掉 status='gone'

to = '<m>'
  发送者必须是 alive 的成员（人 → 403）
  m 等于发送者 → 400 bad_request（不能给自己发一对一）
  目标必须是 alive 的成员（gone → 410）
  收件人 = [m]
```

群存在性检查必须与写入同事务，否则并发删掉最后一个子成员之后，仍可能写入一条永远没有收件人的消息。

### 5.2 @ 的规则

@ **不决定收件人**，只决定谁被标记为"被点名"。

| 规则 | 说明 |
|---|---|
| 不 @ | `mentions` 为空。收件人全部 `mentions_me=false` |
| `@all` | 客户端写 `mentions: ["all"]`。服务端展开成群的当前成员（owner + children，快照），全员 `mentions_me=true`。`"all"` 是 `mentions` 里唯一的魔法值，与成员 id 不会冲突 |
| `@某人` | 那个人 `true`，其余 `false` |
| 范围 | `@` 的目标必须是该群的当前成员；显式 `mentions` 数组里出现群外目标 → 400 `unknown_mention` |
| 正文 | **不解析正文里的 `@`。** 点名只来自显式 `mentions` 数组。适配器想支持"从正文里认名字"，自己认完再填数组 |
| 一对一 | `mentions` 必须为空，否则 400（一对一没有点名的概念）|

`mentions_me` 的严格定义：**这条消息的 mentions 集合包含我**。不 @ 的消息不算；我自己发的消息不算（发送者不入 inbox）。

### 5.3 读历史

```
GET /v1/messages?to=<会话 id 或写侧形态>&before=<seq>&limit=50
```

- 可见性按 §3.5
- `limit` 默认 50，上限 200（超出按 200）
- `before` 省略 ⇒ 该会话最新的 `limit` 条
- 返回 `{items, next}`：`next` 是继续往前翻的 `before` 值；**翻到头时 `next` 为 `null`**，客户端不必再发一次空请求去试探
- 历史**不受**投递过滤：能读这个会话就能读它的全部历史，包括它被创建之前的

投递是快照（成员被创建之后收不到更早的消息），读取是可见范围内的全量——两件事并存。

### 5.4 人的发言

人发消息走同一接口，`to` 只能是 `g:<o>`。落库时 `sender_kind='human'`，读取时随消息返回，适配器据此区分"上级说的"和"人说的"。

## 6. poll：消费、跳过与回补

### 6.1 语义

**`poll` 自动消费**：取走即推进，没有单独的 ack。没有 `since` 参数，服务端记着位置。

代价是 at-most-once：成员取走一批后在处理中崩溃，那批不会重投。**消息本身不删**，需要时可以用 `GET /v1/messages?to=&before=` 补读。这是刻意的取舍。

### 6.2 请求

```
GET /v1/poll?wait=25&limit=20&types=message,control
```

| 参数 | 默认 | 上限 | 说明 |
|---|---|---|---|
| `wait` | 25 | 50 | 挂起秒数，超时返回空列表 |
| `limit` | 20 | 50 | **消息与指令各自**最多返回多少条 |
| `types` | 全部 | — | 只取其中一类；被排除的那一类不会被消费 |

越界一律静默截断：`limit > 50` 按 50，`limit < 1` 按 1，`wait > 50` 按 50，`wait < 0` 按 0。

`types` 是另一回事：只接受 `message` / `control` / `all`（缺省即 `all`）。出现其它值 → `400 bad_request`。**不能静默当成空集合**——那会让客户端安静地停摆，看起来和“没有新东西”一模一样。

### 6.3 响应：一个列表，三种 item

```json
{
  "items": [
    { "kind": "control", "control_seq": 17, "id": "c_7f3a91c0", "from_id": "sys",
      "cmd": "sys.terminated", "payload": {"reason":"task complete"},
      "reply_to": null, "created_at": 1730000000456 },

    { "kind": "gap", "to": "g:m_abc123", "count": 12, "before": 88, "mentioned": 2 },

    { "kind": "message", "to": "g:m_abc123", "seq": 89,
      "from_id": "m_9f8e7d", "from_name": "quiet-otter-7f3a", "from_kind": "member",
      "body": "完整正文", "mentions_me": true, "from_parent": true,
      "at": 1730000000123 }
  ],
  "control_pending": 0
}
```

**顺序固定**：指令（按 `control_seq` 升序）→ gap（按 `conv_id` 升序）→ 消息（按投递顺序升序）。

`control_pending` = 本批没有取走的待送达指令数（因为 `types` 排除了 control，或超过 `limit`）。

### 6.4 gap

积压超过 `limit` 时，只投递**最近的 `limit` 条消息**，更旧的按会话各自折叠成一个 `gap`：

| 字段 | 含义 |
|---|---|
| `to` | 哪个会话有被跳过的内容 |
| `count` | 这个会话里被跳过了几条 |
| `before` | 回补锚点：调 `GET /v1/messages?to=<to>&before=<before>` |
| `mentioned` | 被跳过的部分里有几条点了我的名 |

**`before` 的取法**：该会话在本批里有保留项时，取最早那条的 `seq`；一个保留项都没有时，取"最近一条被跳过消息的 `seq` + 1"。

**`before` 是历史游标，不是精确窗口。** `GET /v1/messages` 返回的是 `before` 之前的最近 `limit` 条，里面可能还包含更早的、当时没投递给我的消息。要精确圈定"被跳过的那一段"，用 `before` 往上翻，直到撞上自己手上已有的编号。

**每个会话至多一条 gap，且一定排在该会话自己的消息之前。** 因为 `poll` 取的是投递顺序的**后缀**：被跳过的全部早于被保留的，所以对每个会话而言被跳过的都是它自己的一个连续前缀。

**gap 是一次性信号**：agent 忽略它，下一批不会再给。兜底不靠它——`GET /v1/conversations` 对每个会话给出 `last_message_seq`，和自己手上最高编号一比就知道落后多少。

### 6.5 结算算法

```
BEGIN IMMEDIATE;
  if 我是 gone:
      取全部 pending receipts → 置 delivered
      若有：COMMIT，返回这些 control items（不加 messages、不加 gap）
      若无：COMMIT，返回 410 member_gone
  else:
      if types 含 control:
         取最多 limit 条 pending receipts（按 control_seq）→ 置 delivered → control items
      if types 含 message:
         取 inbox 里 seq > cursor 的后缀：
           total ≤ limit → 全取
           total > limit → 取最新 limit 条，其余按 conv_id 折叠成 gap
         cursor 推进到本批最大 inbox.seq（本批没有消息则不推进）
      COMMIT，返回 items
```

**等待不能持有写事务**：先做一次上面的检查；没有东西就释放事务、挂起等待；被唤醒或超时后再开一次新事务重查。长等待期间数据库不能被锁住。

### 6.6 单飞

同一成员同一时刻只允许一个挂起的 `poll`，第二个返 `409 poll_in_progress` **并带 `Retry-After: 1`**。本设计以"一个成员一个进程"为前提；如果适配器重启时旧 poll 还没断，就会撞上 409，重试即可。

### 6.7 投递正文

**平台不截断正文。** 一条消息最多 `MAX_MESSAGE_BODY_BYTES = 64 KiB`（字节，写入时就拒绝超限），
所以 `body` 永远等于存的正文——投递和 `GET /v1/messages` 给出同一个字符串。

这个决定改自 0.4.0：0.3 的 `preview` 把正文切到 **200 code points**，不省略号、不标记、不报长度。
实测现网 quant 组织 1108 条成员消息里 **94.9% 超过 200**，也就是说绝大多数消息以半句话的状态
进入模型上下文，而模型不知道少了东西。**为什么不是加 `truncated` 标志**：平台不截断，标志恒为 false，
是一个会腐烂的承诺；真正需要管的是"注入多少进上下文"，那是适配器的预算问题，由适配器自己截断并显式标注。

两个布尔是给适配器做廉价预过滤用的，服务端不做相关性判断：

- `mentions_me`：这条消息的 mentions 集合包含我（§5.2）
- `from_parent`：`from_id` 等于我的 `parent_id`。人发的恒为 `false`；兄弟发的为 `false`

## 7. 指令与通知

### 7.1 发送

```
POST /v1/control { to, id, cmd, payload?, reply_to? }
```

| `to` 的形态 | 目标 |
|---|---|
| `"m_x"` | 单个成员 |
| `["m_a","m_b"]` | 指定几个成员 |
| `"g:<o>"` | 群(o) 除发送者以外的全部成员 |

**可达范围**：每个目标都必须与发送者同群（父、子、或同父兄弟）。人是例外——人可以发给任何成员。`g:<o>` 里的 `o` 必须是发送者自己或它的父；人可以用任何存在的群。

失败要分清，否则客户端不知道是重试还是放弃：

| 情形 | 返回 |
|---|---|
| 目标成员 id 从未存在 | `404 not_found` |
| 目标已 `gone` | `410 member_gone` |
| 我是成员，且有目标与我不在同一群 | `403 forbidden` |
| `cmd` 长度不在 1–200 | `400 invalid_cmd` |

**内容完全不被解释**：`cmd` 是一行自由文本——可以叫 `pi.pause`，也可以是"先把测试跑通再回话"。平台不校验它是什么，不分类，不维护白名单。`payload` 可选，不透明 JSON，≤ 64 KiB。`id` 必填，与 `from_id` 组成幂等键；重发返回原 `control_seq`。

**可达不代表服从**：平台只保证送达。

### 7.2 通知怎么和指令区分

平台自己只在成员被删除时发一条终止通知，以 `from_id='sys'` 的身份发出。

**平台不靠命令文本区分通知和指令**，只靠发送者：`from_id='sys'` 就是平台，其余是成员或人。所以不需要"入站命令不得以 `sys.` 开头"这类内容规则——那等于平台在解释内容。适配器收到 `cmd` 以 `sys.` 开头但 `from_id` 不是 `sys` 的指令，应当当作普通指令（或忽略），这是适配器的事。

| 通知 | 时机 | payload |
|---|---|---|
| `sys.terminated` | 成员被置为 `gone` 时（同事务）| `{reason, terminated_by}` |

### 7.3 送达状态

```
GET /v1/control?since=<control_seq>&limit=50
```

只返回**我自己发出的**指令。`since` 是排他游标，按 `control_seq` 升序；`next` = 本批最大 `control_seq`，没有更多为 `null`。人也能查自己发的。

```json
{ "items": [
    { "seq": 17, "id": "r1", "to": "g:m_abc123",
      "receipts": [ { "to_id": "m_abc123", "state": "delivered",
                      "delivered_at": 1730000001123 },
                    { "to_id": "m_9f8e7d", "state": "pending",
                      "delivered_at": null } ],
      "created_at": 1730000000456 } ],
  "next": null }
```

**不返回 `cmd` 与 `payload`**——概念稿说指令"不进 agent 的历史"，对发送方返回内容会让这句话变成假的。没有"已读"这回事：`delivered` 只表示对方把它取走了。

#### 人的全量读权

```
GET /v1/control?all=true&since=&limit=&from_id=&to=
```

- **仅 `human` token**。只要请求里出现 `all` 参数——不论值是什么（`true` / `1` / `TRUE` / 空 / `false`）——成员一律 `403 forbidden`。**按参数是否出现判定，不解析真值**：`all=0`、`all=no`、`all=` 这类写法没有公认语义，让它们落到“不是全量视图”会变成一个静默的越权面
- 返回跨成员的全部指令，**并且包含 `cmd` 与 `payload`**
- 人带**任何值**的 `all`（含 `false`、`0`、空值）都得到全量视图——同样按参数是否出现判定，不解析真值
- `from_id` / `to` 是可选的过滤器，供界面重建某条有向边的时间线
- 分页与默认视图相同：`since` 排他、`next` 为本批最大 `control_seq`

**历史行的 `to_json` 可能不是 JSON。** `e03af1a` 之前，`sys.terminated` 把目标成员 id
当裸字符串写进 `to_json`（`m_635f7e`），而两个读侧都无条件 `JSON.parse`——删一个成员就把
“解释这次删除的日志”打成 500。现在有三层：

1. 写侧一律 `JSON.stringify(to)`（`sys.terminated` 也是）；
2. 读侧容错：解析失败就原样返回那段文本，不抛；
3. `openDatabase` 开库时一次性回填非 JSON 行：
   `UPDATE controls SET to_json = json_quote(to_json) WHERE json_valid(to_json) = 0`。
   没有这一步，`?to=` 过滤（比较 `to_json` 与 `JSON.stringify(to)`）会静默漏掉旧行——
   容错解析只救得了展示，救不了比较。

回归测试：`test/legacy-control-target.test.ts`（旧行在开库前写入 → 回填后 `?to=` 能查到；
运行中写入的旧行 → 读侧不 500）。

```json
{ "items": [
    { "seq": 17, "id": "r1", "from_id": "m_abc123", "to": "m_9f8e7d",
      "cmd": "pi.abort", "payload": {"reason":"stalled 12m"}, "reply_to": null,
      "receipts": [{"to_id":"m_9f8e7d","state":"delivered","delivered_at":1730000001123}],
      "created_at": 1730000000456 } ],
  "next": null }
```

**为什么人可以看。** 人不属于任何群，是这个系统里唯一的全见者。指令不进 agent 的上下文是有意的、继续保留；但它必须进人的视野——否则"上下级在命令什么"无从追查，一个卡住的成员是被错误指挥还是自己不行，也分不出来。

**这不违反"平台不解释指令内容"。** 平台依然不解释、不分类、不校验；它只是把原文交给唯一有权看的那一类主体。

**这也不会把指令变成第二个消息流。** 指令仍然不属于任何会话，没有 `conv_id`，不进 `messages`、不写 `inbox`。人看到的是"按有向边发生过的操作"，不是"某个空间里大家说过的话"。

## 8. 生命周期

### 8.1 创建

```
POST /v1/members { name?, request_id }
```

- 调用者必须 `alive`（`gone` → 410）
- `parent_id` = 调用者。平台不检查数量与层数
- `name` 不给时生成 `形容词-名词-4hex`，冲突重试
- **不带任务简报**：创建只建结构，简报随后由创建者用一对一发给它
- 重发同一 `request_id` 返回原成员，**不含 token**（明文只存哈希，无法二次返回）；需要 token 时走 `POST /v1/members/{id}/token`

### 8.2 删除

```
DELETE /v1/members/{id}
```

- 权限判定沿 `parent_id` 链走**曾属子组织**（含 `gone`），先于 §3.3 的活子组织检查；跨子树 → `403`
- 根 → `409 root_protected`
- 整棵子树一起删，没有"只删中间节点、把子成员挂到上面"这种模式

```
BEGIN IMMEDIATE;
  -- 1. 清掉这些成员除终止通知外的 pending receipts：
  --    已决定要删的成员，旧指令不再有意义，也不该继续占着队列
  -- 2. 逐节点插一条 from_id='sys' 的 sys.terminated + 对应 receipt
  -- 3. 整棵子树置为 gone
  UPDATE members SET status='gone', gone_at=?, gone_reason=?
   WHERE id IN 曾属子组织(id) AND status='alive';
COMMIT;
```

- 级联在**一个事务**里完成，所以不存在"删到一半"的窗口：不会有成员在级联过程中创建出新的子成员，也就不会有孤儿。这是这里不需要中间态的原因——事务本身已经保证了互斥
- 重复删除已 `gone` 的成员 → `200`，幂等（靠曾属子组织判定），且 **`terminated` 仍返回同一批 id**——重试的客户端要能看出“上次那批已经删了”
- **提交后立刻唤醒这些成员挂起的 long-poll**：它们要么拿到 `sys.terminated`，要么直接拿到 `410 member_gone`。不唤醒的话，被删成员得等 `wait` 超时才知道自己已经没了

### 8.3 状态机

```
spawn ──▶ alive
            │
            │ DELETE（目标在曾属子组织内）
            │ 同一事务：清旧 receipt → 入队 sys.terminated → 整棵子树置 gone
            ▼
          gone     终态。不再接受任何写入（消息、指令）
                 → poll 只服务这条 sys.terminated
                 → 取走后（无 pending）poll 一律 410 member_gone
```

- `gone` 的 token **仍可用于 `poll`**，其它端点一律 410
- `poll` 返回 410 的条件：`status='gone'` **且** 没有 pending receipt
- 删除时清掉旧 receipt，保证"剩的只有终止通知"，于是 `poll` 必然把它取走，取完即无 pending，410 一定可达
- `gone` 之后不再接受写入是硬规则：否则 pending 永远清不掉，410 永远不可达，适配器只能靠超时猜自己该退出

### 8.4 恢复坐标

```
GET /v1/whoami
```

- 成员：`{kind:'member', member:{...}, groups:[{to,owner}], dms:[{to,peer}], last_seen_at, server:{version, platform_id}}`
- 人：`{kind:'human', human:{...}, conversations:[{to,kind}], last_seen_at, server:{version, platform_id}}`

会话重启、env 丢失时，只要有 token 就能拿回全部坐标。

### 8.5 成员消失由谁发现

平台不判断存活（§9），所以"某个成员的进程死了"这件事，发现责任在适配器：

| 情形 | 谁发现 | 怎么做 |
|---|---|---|
| 子进程退出 | 拉起它的适配器 | 它知道退出码，直接 `DELETE /v1/members/{id}`。这是结构操作，平台负责发终止通知并级联 |
| 适配器自己也挂了（宿主崩、pane 被关） | 平台之外的一方 | 人手动删，或由父成员按下面的阶梯处理 |
| 成员没死但卡住了 | 父成员自己 | 见下面的阶梯 |

**心跳与"它是死是活"是两件事。** 心跳证明的是"喂心跳的循环还在"，不证明 agent 在干活；把一个成员判定为"不在了"、以及因此要不要重建，仍然由父成员决定（§9.1 给了事实，§11 的阶梯给了用法）。

**父成员可用的判定阶梯**（适配器层；平台只提供事实，不预设阈值）：

1. 我发给它的指令还是 `pending` 吗 → `GET /v1/control`。没送到，说明它没来取。
2. **它还在打心跳吗** → `GET /v1/members/{id}` 的 `heartbeat_at`（§9.1）。这一条是**唯一能在进程被强杀之后仍然可见**的信号。
3. 它最近有活动吗 → 同一个响应的 `last_seen_at`（任何请求都刷新它，所以它只能当辅助证据）。
4. 我是不是已经等得太久 → 阈值由父自己定。
5. 都指向"它不在了"，再考虑重建：`DELETE` 它的子树，然后 `POST /v1/members` 建一个新的。

### 9.1 心跳

`PUT /v1/members/{id}/heartbeat` 只写 `heartbeat_at`。它是**唯一**写这一列的路径；`last_seen_at` 与它互不替代。

- **谁能写**：只有成员自己（`id` 必须等于调用者）。
- **多久一次**：由适配器决定（适配器默认 15 s）。平台不规定周期，也就不持有阈值。
- **平台不推论**：不派生 `online` 字段，不把成员标成离线，不做任何状态迁移。它只回答"最后一次心跳是什么时候"。
- **为什么值得一个专用列**：`last_seen_at` 会被**任何**鉴权请求刷新，包括工具里的一次 `pg_say`——所以它回答的是"这个成员做过事吗"，
  而心跳回答的是"**喂心跳的那个循环还活着吗**"。一个循环卡死但还能跑工具调用的成员，两者会给出相反答案，而父级需要后者。
- **它对"进程被强杀"有效**：`kill -9`、OOM、宿主重启时不会有任何请求发出，也不会有退出报告；心跳的**缺席**是此时唯一可见的事实。
- **它不能证明"在干活"**：一个成员可以一边正常心跳一边被 provider 429 卡住。那是 `error`/`stalled` 的领域，属于适配器。

**长 `poll` 的超时返回就是天然的 tick。** 一个挂着的 `poll` 在 `wait` 秒后返回空列表，那本身就是"这段时间什么都没发生"的信号。父的适配器可以在连续几次空返回之后触发一次检查，平台不需要加任何定时器或新接口。

**`last_seen_at` 的偏误是单向的。** 一个正在长时间干活、不轮询的成员会显得"很久没动静"，上一次活动可能停在几天前，但它完全正常。所以这个信号只能用来**怀疑**，不能用来**判定**，更不能作为删除的唯一依据——删除是不可逆的。

## 9. 活动时间

`last_seen_at` 在任何认证成功的请求上刷新，**在请求开始时单独一条 UPDATE 完成，不进任何业务事务**（否则一个挂 25 秒的 long-poll 会让活动时间在整段时间里都不更新，或者反过来把它算进业务事务里回滚掉）。

**它不是存活判断**，两条纪律：

1. **不派生任何存活状态。** `last_seen_at` 与 `heartbeat_at`（§9.1）都只以时间戳的形式暴露；平台不计算 `online`/`offline`、
   不设阈值、不据此改 `status`。心跳接口的存在不改变这条：平台收下的是一条时间，不是一条判断
2. 不暴露 `online` / `offline`，只暴露时间戳

## 10. API 参考

```
POST   /v1/bootstrap             创建第一个成员（成为根）
POST   /v1/humans                创建一个人（仅回环）
GET    /v1/whoami                我的坐标
GET    /v1/health                健康检查
POST   /v1/members               创建子成员
GET    /v1/members/{id}          单个成员详情
DELETE /v1/members/{id}          删除子组织（整棵子树）
POST   /v1/members/{id}/token    重发 token
PUT    /v1/members/{id}/heartbeat 心跳：只写 heartbeat_at
GET    /v1/tree                  组织图（所有主体可见）
GET    /v1/conversations         我能参与的会话
POST   /v1/messages              发消息（群 or 一对一）
GET    /v1/messages              读历史（按会话往前翻）
GET    /v1/poll                  消费式拉取（指令 / gap / 消息）
POST   /v1/control               发指令
GET    /v1/control               查我发出的指令的送达状态
```

全部 `/v1`，JSON 收发，`Authorization: Bearer <token>`。没有二进制端点。所有响应带 `server_version`。

### 10.1 错误契约

```json
{ "error": { "code": "no_such_group", "message": "...", "detail": {} } }
```

| HTTP | `code` | 场景 |
|---|---|---|
| 400 | `bad_request` / `unknown_mention` / `invalid_cmd` | 参数问题；@ 到群外；一对一带 mentions；给自己发一对一；`cmd` 长度不在 1–200 |
| 401 | `invalid_token` | token 缺失或不可识别 |
| 403 | `forbidden` | 不在结构范围内；人尝试一对一或结构操作；指令跨群 |
| 404 | `not_found` / `no_such_group` | 成员 id 从未存在；群不存在 |
| 409 | `poll_in_progress` / `name_taken` / `root_protected` / `already_bootstrapped` | 状态冲突；`poll_in_progress` 带 `Retry-After: 1` |
| 410 | `member_gone` | 对 gone 成员写入；gone 成员已 drain 完的 `poll` |
| 413 | `payload_too_large` | body 或 payload 超限 |
| 503 | `starting`（或 `{status:'starting'}`） | 只在启动窗口内：监听已绑定、数据库还没打开。`/v1/health` 答 `{status:'starting', version, uptime_ms, platform_id}`，其余路径答标准错误封套（§11.0） |

**401 与 410 必须可区分**：适配器靠它决定"重试"还是"退出进程"。

### 10.2 引导与身份

| 方法 | 路径 | 鉴权 | 请求 | 响应 |
|---|---|---|---|---|
| `POST` | `/v1/bootstrap` | 无（已有活着的根 → 409 `already_bootstrapped`）| `{name?}` | `{member, token}` |
| `POST` | `/v1/humans` | 仅回环 **且** 用 admin token 认证 | `{name?}` | `{human, token}` |
| `GET` | `/v1/whoami` | 成员或人 | — | 见 §8.4 |
| `GET` | `/v1/health` | 无 | — | `{status, version, uptime_ms, platform_id}`；`platform_id` 就是平台目录名，且与 `meta.platform_id` 恒等（不一致时拒绝启动，见 §4）。数据库打开前同一路径答 `503 {status:'starting', version, uptime_ms, platform_id}`，身份字段相同（§11.0） |

### 10.3 组织

| 方法 | 路径 | 鉴权 | 请求 | 响应 |
|---|---|---|---|---|
| `POST` | `/v1/members` | alive 成员 | `{name?, request_id}` | `{member, token}`；重放时无 `token` |
| `GET` | `/v1/members/{id}` | 任何主体 | — | `{id,name,parent_id,status,is_root,child_count,groups,last_seen_at,heartbeat_at,created_at}` |
| `PUT` | `/v1/members/{id}/heartbeat` | 只有该成员自己 | — | `{heartbeat_at}` |
| `DELETE` | `/v1/members/{id}` | 目标在曾属子组织内 | — | `{terminated:[ids]}` |
| `POST` | `/v1/members/{id}/token` | 目标是我的直接子成员 | — | `{token}`（旧 token 立即失效）|
| `GET` | `/v1/tree` | 任何主体 | — | `{nodes:[{id,name,parent_id,child_count,last_seen_at,heartbeat_at}]}` |

**人的创建**：`POST /v1/humans` 使用与其它端点相同的 `Authorization: Bearer` 头，但里面必须是环境变量 `PIGROUPS_ADMIN_TOKEN` 的值。

- 变量未设置 → `403 forbidden`
- 传成员 token → `403 forbidden`（永远不够，回环也不行）
- 传 admin token → 正常创建

理由在概念稿 §6：不能让人这个身份由 agent 申请。仅凭“回环”不够——所有 agent 适配器都与服务端同机，也在回环上。

`GET /v1/members/{id}`：`child_count` 只计活子成员；`groups` 是它所属的群；`status='gone'` 的成员仍然返回 `200`，`404` 只表示 id 从未存在过。

`GET /v1/tree`：只列 `alive` 成员（概念稿 §4.4「只显示存在的成员」），因此没有 `status` 字段、不裁剪、不分页。已删除成员从图上消失。

### 10.4 会话与消息

| 方法 | 路径 | 鉴权 | 请求 | 响应 |
|---|---|---|---|---|
| `GET` | `/v1/conversations` | 成员或人 | — | `{items:[{to,kind,label,owner?,peer?,last_message_seq,last_at}]}` |
| `POST` | `/v1/messages` | 见 §5.1 | `{to, body, mentions?, meta?, client_msg_id?}` | `{to, seq, recipients, created_at}` |
| `GET` | `/v1/messages` | 见 §3.5 | `?to=&before=&limit=` | `{items:[{to,seq,sender_id,sender_kind,sender_name,body,meta,mentions,created_at}], next}` |
| `GET` | `/v1/poll` | 成员 | `?wait=&limit=&types=` | `{items, control_pending}` |

**`GET /v1/conversations` 的范围与字段来源**：

```
成员：
  群   = 自己拥有的群（children 非空）+ 父节点的群
  DM   = messages 里 conv_id 以 'dm:' 开头且 sender_id = 我
         ∪ inbox 里 member_id = 我 的行所属的 DM
人：
  全部群 + 全部出现过的 DM
kind   = 'group' | 'dm'
label  = 群取 owner 的 name；成员视角的 DM 取 peer 的 name；人的视角没有 peer，取 `"<a> & <b>"`
peer   = 仅成员视角的 DM 有
空群   = last_message_seq 0、last_at null
```

**没有 `unread` 字段。** 它曾是按消费指针算的未读数，但没有任何客户端用得上：成员持续 `poll`，游标总在底部，它恒为 0；人没有服务端游标，只能拿到 `null`。

两边的未读都由各自的客户端算：成员不需要（`poll` 就是它的收件箱）；人按 `last_message_seq` 减去自己记的游标。留下一个所有人都必须忽略的字段，只会让下一个读代码的人以为平台在维护未读数。

|---|---|---|---|---|

## 11. 运行时与存储

**TypeScript + SQLite，每平台一个进程。**

- Node >= 24 + `node:sqlite`（同步 API，匹配"单进程 + 短事务"）+ 轻量路由（Hono）+ `zod`
- 选 TS 的理由：Pi 适配器本身就是 TS，同一份 zod schema 同时生成服务端校验与客户端类型
- Node 直接运行 TypeScript，没有构建步骤
- long-poll 用进程内事件表（`Map<member_id, Set<waiter>>` + 定时器），不需要外部队列
- 单飞 `poll` 用同一张表维护 `inflight`，进程重启即清空

**一个数据根装下所有平台。** `PIGROUPS_DATA` 是数据根（默认 `./.pigroups`），不是单个平台的目录。本文说的"平台"就是概念稿的 workspace：一个进程服务一个平台。

```
PIGROUPS_DATA（默认 ./.pigroups）
└── platforms/
    ├── .start.lock             # 启动瞬间的互斥文件，正常退出即删
    └── <platform_id>/          自动生成的形如 p_<8 hex>
        ├── pigroups.db         # SQLite WAL
        ├── pigroups.db-wal     # 有未 checkpoint 的提交时才存在
        ├── pigroups.db-shm
        ├── endpoint.json       # 最近一次绑定到的端口、pid、版本（§11.0）
        └── server.log          # 每次启动追加一行
```

**平台的定义**：`platforms/` 下**含 `pigroups.db`（且它是文件）**的目录。空目录、只剩 `server.log` 的目录、失败的残骸都不算平台，不参与下面的选择。

平台 id 由谁决定：

| 启动时的情况 | 行为 |
|---|---|
| 给了 `PIGROUPS_PLATFORM_ID` | 用 `platforms/<它>`；目录不存在就建。值必须是单个目录名：`.`, `..`、含路径分隔符（`/`、`\`）、等于锁文件名，一律**拒绝启动**；空串按"没给"处理 |
| 没给，`platforms/` 里恰好一个平台 | 复用它（方便单独 `npm run serve`） |
| 没给，`platforms/` 里一个都没有 | 生成一个新的 `p_<8 hex>` 并建目录 |
| 没给，`platforms/` 里多于一个 | **拒绝启动**，错误里列出已有 id；不猜 |
| 根上有 0.2.0 的 `pigroups.db`，`platforms/` 里还没有平台 | **接纳**：把它连 `-wal`/`-shm`/`-journal` 一起搬进 `platforms/<id>/`（显式给了 id 就用它，否则生成新 id），随后由打开流程补 `meta` |
| 根上有 0.2.0 的 `pigroups.db`，`platforms/` 里已有平台 | **拒绝启动**，即使显式给了 `PIGROUPS_PLATFORM_ID` 也一样——根上那份库是没人认领的数据，不能替调用者决定忽略它 |
| 接纳到一半崩溃过：某个目录只有侧车（`-wal`/`-shm`/`-journal`）没有库 | 接纳**落进那个目录**，把库交给它自己的 WAL，而不是另建一个平台把 WAL 变成孤儿；这种目录多于一个时**拒绝启动**并列出它们 |
| 根库与 `platforms/` 不在同一个文件系统 | **拒绝启动**（`rename` 会 `EXDEV`），错误里说明要先把数据根挪到一个文件系统 |

接纳的次序是**侧车先、主库最后**：主库留在根上就是"接纳还没做完"的标记。因此半个接纳留下的状态是"根上有库、某个目录里有它的侧车"，上表里"接纳到一半崩溃过"那一行处理的正是这件事。

**启动锁。** `platforms/.start.lock` 序列化"看一眼再决定用哪个 id"这段临界区（选 id、建目录、开库）。同一数据根的两个进程同时启动时，后来的那个**立刻拒绝**并报出持有者 pid，不排队、不猜。持有人进程还活着就尊重这把锁，**不管文件有多旧**：临界区里可能正在恢复大 WAL，墙上时钟不该决定谁进得去。只有两种情况算遗弃——持有者 pid 已经不在了，或者文件内容根本读不出来（死在"建好文件、还没写内容"之间）且文件本身超过 60 秒。锁只覆盖启动，不参与运行期的单实例判定（那是 §11.0 的事）；它也不在显式 id 且根上没有待接纳旧库时获取，所以一个数据根上的多个平台可以同时开机。

`PIGROUPS_DATA` 显式给了就照它，但内部仍然是 `platforms/<id>/` 这一层；`PIGROUPS_PLATFORM_ID` 是唯一的平台选择变量。多个平台可以共用一个数据根；它们各自有独立的 `pigroups.db`，互不共享树、消息、指令或 token。没有 blob 目录、没有群目录。**没有内置 UI**——人看的界面是一个外部客户端，用人的 token 调同一套接口。

### 11.0 单实例：端口就是锁

**一个平台在同一时刻只能被一个进程服务，这条由监听端口强制，不由锁文件强制。**

启动时先确定候选端口：

| 情况 | 第一候选 |
|---|---|
| `platforms/<id>/endpoint.json` 存在，且其中的 `platform_id` 与本平台一致 | 记录里的 `port` |
| 没有记录（新平台，或记录被删） | `PORT`（默认 `7717`） |

顺序上唯一的例外是 0.2.0 旧库的**接纳**：它必须在打开数据库之前把文件搬进 `platforms/<id>/`，
而且这一步仍在 `.start.lock` 里完成。因此"绑定先于数据"精确地说是"绑定先于打开或迁移数据库"；
接纳之后即使所有候选都绑不上，库已经在正式位置，不会丢。

然后循环：

1. **真正 `listen(n)`，成功就一直持有这个 socket。** 绑定成功即所有权，从那以后到进程退出都不释放。
2. 绑定成功 → **先写 `endpoint.json`，再打开数据库**，最后挂正式路由。
3. 绑定失败且错误是 `EADDRINUSE` → 探测 `n` 上的 `GET /v1/health`，间隔 150 ms 再探测一次：
   - 任一次报告了**相同的 `platform_id`** → 这是同一个平台，本进程以**退出码 2** 退出，不碰数据；
   - 任一次给出**有把握的"不是我们"**——另一个 `platform_id`，或一个不是 PiGroups 的 HTTP 响应 → `n + 1`，回到第 1 步；
   - 两次都没有答复，但 `endpoint.json` 记着**本平台、本端口、且那个 pid 还活着** → 这是同一个平台正在初始化，退出码 **2**；
   - 其余"两次都没有答复"→ **拒绝启动**，错误里写明端口和两次探测的结果。
   - 绑定失败而探测得到 `ECONNREFUSED`（端口上没人应答）：说明持有者绑在了 `127.0.0.1` 之外的地址。
     重试一次仍然如此就拒绝启动，不前进——无法确认它是不是同一个平台。
4. 其它监听错误（`EACCES`、地址不可用等）→ 直接失败，不换端口。
5. 候选超过 65535 → 失败，错误里给出起始候选。

**为什么"两次都没答复"不是换端口的理由。** 端口被占住却答不上来，最常见的解释不是"别的程序"，而是"同一个平台的另一个进程刚刚 bind，正在打开或迁移数据库"：`node:sqlite` 是同步 API，那段时间事件循环被占住，探测连接排在 backlog 里，直到初始化结束才有应答。此时跳到 `n + 1` 会得到第二个进程、同一份数据库，正是这条规则要防的事。**只有拿到"不是我们"的正证据才允许前进**；"问不到"不是证据。

**绑定之后、数据库打开之前就报身份。** 监听器先挂一个只回答身份的 handler：`GET /v1/health` → `503 {status:'starting', version, uptime_ms, platform_id}`，其它路径 → `503 {error:{code:'starting'}, server_version}`。绑定与打开数据库之间故意让出一个事件循环回合，所以落在那个窗口里的探测能得到身份。`openDatabase` 仍是同步的：落在它执行期间的探测只能排在 socket backlog 里，等到初始化结束才有应答——这也是"问不到不等于不是我们"的原因之一。数据库打开后同一个端口换成正式应用，`/v1/health` 变成 `200 {status:'ok', ...}`。

启动失败（拒绝、绑定错误、打开数据库失败）不会留下一个空平台目录：只有目录确实是空的才删掉；
已经接纳了旧库或写了 endpoint 的目录保留。删掉 `endpoint.json` 可以让平台下次从 `PORT` 重新找端口，
但**必须先停掉正在服务的进程**——否则继任者会在另一个端口打开同一份数据库，端口就不再是锁。

**`endpoint.json` 是提示，不是锁。** 它记录 `{platform_id, port, version, pid, updated_at}`，用临时文件 + `rename` 原子写入，权限 `0600`。进程被 `kill -9`、OOM 或宿主重启后文件还在，下一次启动照常按它的端口尝试：空闲就 bind 成功，被别人占了就按上面的规则处理。它唯一的权威用途是让**同一个平台的下一次启动落在同一个端口上**——否则两个传了不同 `PORT` 的启动者永远不会相遇，端口也就当不成锁。删掉它等于允许平台重新从 `PORT` 开始找端口。

**退出码。** `0` 正常退出（`SIGTERM`/`SIGINT`）；`1` 启动失败；`2` 同一个平台已经由另一个进程服务（本进程没有绑定、没有打开数据库、没有写记录）。

**部署**：一个平台 = 一个进程 = 一个端口，现在由绑定强制；一个数据根可以放多个平台，它们各有各的 `endpoint.json`，互不竞争。端口可以随占用情况变化，客户端不应把某个端口当成平台身份——身份是 `platform_id`，地址是 `endpoint.json` 的当前值。

端口变化是**恢复事件**，不是常态：正常重启会回到记录里的端口，只有它被别人占住（或记录被删）时平台才前进。已经在连的客户端手里是旧地址，适配器不会替运行中的进程改环境变量；下一次 `pg_org_start` 或成员重开时收敛到新地址。

### 11.1 为什么没有迁移框架

需要"更新"的东西有两类：可重复执行的建表（`CREATE TABLE IF NOT EXISTS`），和一次性、幂等的行级回填（旧库补 `meta` 三行、`controls.to_json` 回填）。两者都是 `openDatabase` 里的几行代码，为它们造一个只服务于它们的框架是生造的需求。schema 兼容性理论上可以从 server 版本推出来，但我们**不做这个推导**；等到真需要兼容性那一天再设计，那时才有多于一个东西要迁移，`meta` 里也没有 `schema_version` 可用。

## 12. 恢复与一致性

| 场景 | 行为 |
|---|---|
| 服务端重启 | 挂起的 long-poll 全断开；客户端重发即可。消费指针在库里 |
| 成员重启 | `GET /v1/whoami` 重建坐标。已取走未处理的消息不会重投（at-most-once），需要时按会话翻历史 |
| 重发消息 | `client_msg_id` 幂等：返回原 `seq`，不产生第二条 |
| 重发创建 | `request_id` 幂等：返回原成员，不含 token |
| 重发指令 | `(from_id, id)` 幂等：返回原 `control_seq` |
| 一条消息处理失败 | 不影响指令投递（§3.6）|
| 写消息时崩溃 | 群存在性检查 + `conversation_seqs` 自增 + `messages` + `mentions` + `inbox` 同事务 |
| 树变更 | 只影响后续 fan-out；已投递的不变 |
| 队列积压 | 不设上限、不背压。超过 `limit` 的部分折叠成 gap；消息永久保留，随时可按会话回补 |

**必须原子的操作**：

1. `POST /v1/messages`：群存在性检查 + 会话序号自增 + `messages` + `mentions` + N 行 `inbox`
2. `POST /v1/control`：`controls` + 展开后的 N 行 receipts
3. `POST /v1/members`：`members`
4. `DELETE /v1/members/{id}`：清旧 receipt → 逐节点终止通知 + receipt → 整棵子树 `alive→gone`。翻转必须与"之后拒绝写入"同时生效，否则 410 不可达
5. `GET /v1/poll`：receipts 置 `delivered` + 消费指针推进（只改动，不产生新消息）。**等待期间不得持有写事务**

## 14. 开放问题

1. **`messages` 与 `inbox` 都没有清理策略**。消息要永久保留（人要能读全部历史），所以磁盘无上限；`inbox` 行在成员消费后也没有删除时机。需要定一个保留窗口或归档策略。这是去掉背压之后唯一需要盯的地方。
2. **`last_seen_at` 为 NULL**（刚创建、还没发过请求）时组织图显示什么：空、还是创建时间。
3. **`@all` 是发送时刻的快照**：之后新建的子成员收不到这条点名。是否符合预期。
4. **`at-most-once` 是否够用**：如果实测发现"取走未处理"的丢失代价明显，就要回到 fetch/ack 分离。
5. **人的未读只在客户端**：同一人开两个界面时未读不共享。目前接受，如果变成真需求要给平台加回一个只读的水位。
6. **`GET /v1/tree` 不分页**：几十个成员时一屏足够；上到几百个时要么分页，要么改成按子树查询。

## 15. 已定的决定（备查）

| 决定 | 理由 |
|---|---|
| 人的 API 与成员同一套，不设独立通道 | 独立通道等于把 UI 的职责搬进平台；两条读取路径必然出现行为不一致 |
| 平台不带内置 UI | 平台只讲 HTTP/JSON；内置 UI 会把静态资源、CORS、构建产物拖进单体 |
| 每会话独立编号，不暴露全局消息编号 | 全局消息号泄漏"我看不到的会话有多少流量"；回看按会话翻页，用不上它。（指令的 `control_seq` 是另一回事，不泄漏消息流量，保留全局） |
| `poll` 自动消费，不分离 fetch/ack | 简单直接；消息不删，真要补可以按会话翻历史 |
| 只投递最近一批，跳过部分按会话折叠成 gap | 离开很久的成员积压几百条时，全塞进去既无用又撑爆上下文 |
| gap 是一次性信号 | 兜底不靠它：`conversations.last_message_seq` 与自己手上编号一比就能随时自查 |
| 指令不设已读，只报送达 | 已读是给内容用的；指令是控制信号，不是给 agent 看的内容 |
| 指令可达范围 = 群，可批量 | 父↔子、兄弟↔兄弟本质是同一条；批量只是省往返，不扩大可达范围 |
| `cmd` 是自由文本，平台不校验内容 | 平台本来就不解释内容；通知靠 `from_id='sys'` 识别，不靠命令文本 |
| 没有改名 | 名字是历史记录里的稳定标签；改了以后旧消息里的名字会指错人 |
| 没有初始任务简报 | 简报走一对一，进消息历史，事后能查当时派的什么活 |
| 人不能硬止损 | 止损靠外部关进程或发 stop 指令；给人结构操作会破坏"人不在树上" |
| `limit` 默认 20 | 先跑起来，太小再调 |
| 不做心跳，发现成员消失是适配器的责任 | 见 §8.5 |
| 去掉删除的中间态 | 级联是单事务，中间态对外不可观测；事务本身已保证不会产生孤儿 |
| 不设 inbox 上限、不做背压 | 背压会把"某个收件人落后"惩罚到发送者头上；gap 机制本来就能收口积压 |

## 16. 版本

- **版本号只写在 `package.json` 的 `version` 里。** `src/version.ts` 直接读它，代码里没有第二个常量；`test/version.test.ts` 比对 `GET /v1/health` 与 `package.json`，防止有人再写回一个会漂移的副本。库里 `meta.server_version` 是"谁最后一次打开过这份数据"的观测记录，代码不读它做任何判断（§4）。
- **0.x 的两个位各有含义。** 补丁位（`0.x.N+1`）只修不改变契约的缺陷：端点、字段、工具名都不变。次版本位（`0.X+1.0`）用于契约变化：新增或删除字段/端点/接口成员、文档化的行为改变、数据迁移。1.0 之前不套用 semver 的默认含义。
- **平台与适配器同号推进。** 两者作为一套系统开发，`v<version>` 标签记录的是这一对；发布时两边打同一个号。
- **每一次响应都带 `server_version`**，包括错误响应和 404；`GET /v1/health` 的 `version` 是同一个值。适配器启动时对一次版本，就能发现自己和服务端是不是同一代。
- 每个版本的变更写进 `CHANGELOG.md`；打标签前 `npm run typecheck` 与 `npm test` 必须通过。
