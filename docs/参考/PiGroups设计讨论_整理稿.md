# Pi Groups 设计讨论（语音转写整理稿）

说话人 1（00:00:00）

想到一个 AI 的方案，暂且把它叫做 Pi Groups。现在多 agent 的协作，可能需要做扁平的组织，或者说分层的组织。我是想把这些不同的形式都用一种方案来概括，也就是仿照公司的那个 OA 系统或者说钉钉这种形式，来做一个群聊的服务端或者说后台。

虽然我想把它叫做 Pi Groups，但它的整个群聊服务端、与 Pi 的接口，以及可能跟 herdr 的显示，可以是解耦的，也就是说 Pi Groups 也可以应用在别的 agent harness 之上。

所以我想怎么设计呢？最好分为两个方向：一个是后台，用于维护聊天列表、成员列表以及文件列表等资源；另一个是接口，对于每一个成员都有可以交互的 API。分成这两个部分。

后台的部分暂时我认为不用多说，根据 API 就能知道后台应该实现哪些功能，以及如何组织。对于 API，它应该能支持下面这些功能。

第一，创建用户。第一个创建用户的用户可以称作群主，他相当于整个项目经理：如果是扁平架构，他就是项目经理；如果是多级架构，他就是最高级，相当于一个群主。他还可以安排其他的成员作为管理员，去管理下一级实际干活的员工。所以这个接口实现的第一个功能就是成员注册。

第二个功能是与 Pi Groups 的交互。一个成员可以拉起别的 Pi agent 的 session 实例，在创建的时候，它就自动给这个 agent 注册一个 Pi Groups 的成员。

下一个功能就是群聊和一对一的聊天。群聊的话，刚开始所有的成员都要默认进入一个大的群聊。如果是典型的架构，也就是一个或多个 worker 和一个经理，那么所有成员只在这一个群聊里面聊天就可以了。此外，除了群聊，还有一对一的聊天。每个登录的成员都需要有一个自己的名字，比如 hash，或者说用一个形容词加名词这种形式来做自己的名字，这些都是小问题。

在主群聊里发送消息，是所有其他成员都能看得到的；如果是一对一聊天，那么就只有对方才能接收到。

如果整个项目比较大——我记得以前 OpenAI 在可能数学研究上有一个"岛"的概念，一个岛里有写代码的和做 review 的、不同分工的 agent，他们组成一个 group，在一个方向或者说一个思路上前进；不同的岛可能在做不同的思路，但是他们也可以交流。这就要求他们既能在一个大的群聊里面沟通，又能在自己的小的群聊里沟通。

所以注册的时候就可以以管理员的形式注册。这个我还没想好：是只能由群主给一个新的成员一个管理员的权限，还是说注册时候只要以管理员注册就可以有管理员权限。总之对于多层架构，会有多个管理员。

然后可以设计成这样：全局的群聊，只有群主（也就是最顶层的第一个成员）可以指定哪些 agent、哪些成员可以在这个大群里发言。管理员又可以自己创建一个小的群聊，然后自己再创建、发布 agent，把这些实际工作的人拉进这个小的群聊。以那个 OpenAI 的例子为例，一个岛就是一个小的群聊，他们之间做思路的沟通就交给管理员，然后在大的群聊里面交流就可以了。

关于权限就可以这么分：一个成员他能看哪些群聊，以及他又能在哪些群聊里发言。这个拓扑应该在创建时就定好，我觉得没必要让他自己去修改，或者说让别人修改组织架构——可以在一开始就定好。唯一的区别就是两类群组：一个是可以发言的，一个是只能看、不能发言的，从一开始就定死。

具体使用上就有一些问题，尤其是 agent loop 环节：怎么往这个平台上去发言、怎么去写东西，其实都是一个很小的问题。重点是对于一个 agent loop 来说，他什么时候可以发言。在我看来，可以让 Pi agent 提供一个工具，比如这个工具去轮询一下，看看有哪些新的、跟自己相关的发言。如果提到自己，这个工具就可以注入一段很短的提示词，比如说"阅读最近的消息，看看是否跟自己有关"，然后用 JSON 格式输出 yes 或 no。如果输出 yes，就把这段注入的提示词删掉，把这段最近聊天记录贴到上下文里，让 agent 回复就可以了；如果回复是 no，就把这段注入的上下文整个删掉，然后把 recent 未读的那个提示关掉，就相当于已经看过了，但决定不需要回复。不过这些是 agent 他自己的工作，比如 Pi 自己的一个任务目标；对于我们想设计的这个后台来说，我们要知道它要提供的就是一个 recent message 的功能。

还有一个比较重要的，就是在群里面 @ 某个 agent 的功能。这个工具还要提供一个共享的文件空间，对于大的群聊以及各自的小群聊里面都要有一个共享文件。我暂时还没想好，这个共享文件到底是直接告诉 agent 它在实际电脑上的哪个地方，还是把这个文件集中放在一个 agent 看不见的地方，它要用的时候得从这个平台上 fetch 下来。

我又想一下，管理员到底要不要分层，以及管理员到底要不要设计，也有待商榷。如果是多级管理员的话，那这个群聊似乎也要分为高级群聊、低级群聊，这样就很复杂，我认为不要这样做。不如就这样：除了群主有最高的权限，每一个成员在注册的时候就给他定好能否创建新群聊的权限。如果能创建，就说明他可以作为一个 manager，或者说叫 straw boss，也就是边干活也边管理的角色。他创建群聊之后，如果觉得下面还要再创建一级，就在这个群聊里拉新成员的时候给他创建群聊的权限，把这些成员都放到自己的群里，像他别的子级，也就是他下面那些小领导。

如果可以创建新群聊，所有新建的群聊就是不分级的：有一个完整的群聊列表，群主是能看到的，但他其实不需要在乎别的、有创建群聊权限的管理员。别人创建什么群聊，他不需要管。如果需要创建多层结构的话，他基本上只用管顶层的群聊就可以了。

如果分非常多级的话，可以让最末级的叶子成员甚至不要加入这个总的群聊，这是一个新的想法。如果加入总的群聊，也可以在成员名单中……总之就是不要让他再看到跟他无关的、毫无关系的信息。虽然我们之前说可以通过注入 prompt 的方式，来看他愿不愿意或者需不需要回复，但我们可以从根子上杜绝这种方式。而且在实际的公司组织中，你确实作为一个部门的基层员工，是不可能去看到全局的互相的消息的。或者说，这个总的群聊只让群主看人员列表；群主如果识别到这个任务会非常大、会有非常多的人，他就把这个列表设为全局禁言，让所有的 agent 都不能在这里面发言。他再想跟下一级的主管沟通的话，就直接再拉一个主管的群聊就可以了。这些都是可以在里面教他们怎么去做的，我说的是 skill。

所以我觉得我最开始说的"整个架构是固定的"这一点可能也需要改一改：可以创建新的群聊，并且一个成员创建之后，别人可以去改他那个群聊的成员，也就是加入那个群聊。最好是只有部分指定的成员，有把另一些特定成员拉入群的权限。但具体怎么设计还有待商榷，因为我不想引入过多的层级权限关系，把整个设计变得非常复杂。

总之，我希望一个成员可以加入多个群，然后在一个群里面是有一个群主的。但是考虑这样一个问题：假如在第一个群里面 A 是群主、B 是成员，而在另外一个群里面 B 是群主、A 是成员，这样权限关系似乎有点混乱。那么这样我们也不搞得太灵活，把整个组织结构还是改回成树状的。

这样群就有两种：第一种是第一个群主（也就是第一个成员）的大群，里面有所有的人员列表，可以看到一个树状的视图；第二种是他和他的子级以及所有 agent 组成的一个群，也就是普通群——某个 agent 和他子一级的所有 agent 组成的群。其实只要有这两种群就够了。所以现在这整个架构就变得非常清晰，也非常的简单了。

然后比较重要的一点是，除了消息的通道，为了更好的跟 harness 集成，还需要一个控制通道：父跟子和子跟父都能发送一些控制字，这些不会出现在消息流里；也可以在群里广播，或者说一对一地聊控制字。

我希望这个平台应该带一个供 human 查看的视图，并且 human 可以有一个等同于最高级群主的权限，甚至更高的权限，去看任意一个 group 里的聊天，以及在任意一个 group 里面插入自己的聊天，以及看到任意一个上传的文件。这个我可以考虑直接做成一个内置的 Web UI，或者说提供一个 API，然后在外面再做 Web UI。

回到刚才控制字的功能上来说，它主要实现的就是去杀死这个成员：在任务结束或者说不需要的时候，比如一次性的上下文、一次性的成员，给他发 quit 的命令。然后这个由比如 Pi 的 harness 自己的一个工具去读这个控制字，来使用这个控制字。

最后一点是关于软件设计上，我觉得可以给它做成一个单体的服务，走标准的（应该叫 FastAPI 吧）或者 HTTP 调用。我不是很清楚，总之可以用 HTTP 调用的方式，让客户端跟这个平台去沟通。这方面就怎么方便怎么来：如果这个平台要求速度的话，可以用 Go 来写；如果要求写起来快的话，可以用 TS 来写。

跟 Pi 集成的话，我觉得就是当最开始起这个平台的那个 agent 的 session，作为最初注册或登录的用户，来作为一个群主。剩下的就是通过 Pi 和这个平台协同来使用：创建新的 session，然后在这个平台里注册新的用户。目前我是跟 herdr 联合使用，它是一个类似于 tmux 的终端复用器，但它对 agent 更友好，可以让 agent 在新的 panel 里去拉起其他的 agent。

这些都是之后才做的事情，我希望先写一个这个平台的设计文档出来。

## 附：原文件自带的 AI 总结

该方案提出基于 OA 系统模式的多层级 AI 群聊平台，支持群主-管理员-成员分层架构，包含成员注册、跨群消息路由、权限控制及文件共享功能。系统通过解耦式接口适配不同 agent 框架，采用控制通道实现非显式消息处理，并设计树状组织视图简化多级管理复杂度。
