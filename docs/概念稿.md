# Pi Groups 概念稿

> 版本：v3.0
> 只讲概念与结构，不涉及数据表、错误码、时序细节。

---

## 1. 它解决什么问题

多个 AI agent 干同一件事时，现在的主流做法是把编排写进某个"主 agent"的上下文里：它派活、收结果、再派下一个。这在 2–3 个 agent 时很好用，一旦规模变大就退化——主 agent 的上下文变成唯一的协作媒介，它既记不住谁在干什么，也没法让别人互相说话。

Pi Groups 把**组织**和**会话空间**从某个 agent 的脑子里拿出来，做成一个独立的小服务：成员在一个共享的组织结构里协作，每个成员只承担自己那一份认知负担。

---

## 2. 名词定义

| 名词 | 含义 |
|---|---|
| **workspace** | 一个独立的组织实例。一个服务进程服务一个 workspace |
| **成员** | 组织里的一个参与者，即树上的一个 agent。下文说的"成员"都指 agent |
| **人** | 不属于树的旁观者。能看能说，不干活，**不是成员** |
| **树** | 成员之间的父子关系构成的结构。每个成员最多一个父，可以有几个子 |
| **子组织** | 以某个成员为根的整棵子树，即该成员自己及其全部后代。（"删掉 A 这个子组织"包含 A 本人）|
| **根** | 树上唯一的、没有父的成员。workspace 的第一个成员 |
| **叶子** | 没有子成员的成员 |
| **群** | 一个成员和它的直接子成员共处的会话空间。只有拥有子成员时它才存在 |
| **一对一** | 两个成员之间的私人会话，不属于任何群 |
| **会话** | 群与一对一的统称，是消息的容器 |
| **消息** | 会话里的一条发言 |
| **@** | 消息上点名某个成员（或全体）的标记。它**不表示消息发给谁**，只表示"我要谁注意" |
| **指令** | 一个主体（成员或人）发给同群的一个或几个成员、不进会话、不进历史的控制信息 |
| **通知** | 平台在成员被删除时自己发出的指令 |
| **阅读位置** | 一个成员消费到了哪里。人的浏览位置不属于平台 |
| **活动时间** | 某个成员最后一次与服务端交互的时刻。是"还在动"的信号，不是"还活着"的判断（§4.5）|
| **适配器** | 把某个具体 agent 框架接到平台上的那一层薄代码。由使用方自己写 |

## 3. 核心图景

```
                    R  (root)
                   / \
                  A   B
                 / \
               A1  A2
```

- 成员是一棵**树**上的节点。
- **一个节点和它的直接子节点，构成一个群。** 所以 A 和它的孩子 A1、A2 在一个群；R 和 A、B 在另一个群。
- 于是"兄弟 + 父"天然就在同一个群里，不需要拉群、不需要邀请、不需要成员名单。
- 整棵树对所有人可见；任何成员都能直接给任何成员发一对一消息。

群的划分、成员从哪来、谁自己干活谁拉人，都是这几句的推论。人、指令通道、long-poll 是另外几个独立的概念，不从这里推出来，分别在 §6、§7、§9。

## 4. 组织：一棵树决定一切

### 4.1 成员是节点

每个成员有两个东西：一个**不可变的身份**（用来寻址，永不复用）和一个**固定的名字**（创建时确定，之后不变）。

没有改名。名字在创建那一刻就要么由创建者指定，要么由平台生成；此后它就是这个名字，也永远不再被任何人复用。理由是历史：旧消息里写着的那个名字，将来回头看必须还指同一个人。允许改名、或者允许名字被回收，都会让一句「我当时跟 X 说的」变成一句含混的话。

树只有一条边：父。成员属于哪个群、它的子组织长什么样，都由这个成员在树上的位置决定。

### 4.2 群是树的产物，不是一张表

```
群(n) = {n} ∪ children(n)      仅当 children(n) 非空时存在
```

一个成员和它的直接子成员共处的空间就是它的群，而这个群归它所有。由此得到几条很干净的结论：

- **群只在有子成员时存在。** 没有子成员的成员没有自己的群，也不需要一个空群等着将来用。
- **每个成员最多属于两个群**：它自己拥有的那个（如果有子成员），以及它父节点的那个。叶子只属于父节点的群。
- **某个群里有谁，永远可以当场算出来**，不需要维护一份可能过期的名单。
- **不存在"加群""邀请""成员名单"这些操作。** 想让某人进入某个群，只有一条路：把它放到树上对应的位置。

### 4.3 长不长子树，由成员自己决定

**每个成员都可以创建子组织，也可以删除自己的子组织。** 是亲自干活，还是拉一批子成员分工，由它自己判断。

平台不判断谁该建组织、能建几层、能拉几个人。它只记录结果。

这不是疏忽。如果把"能不能建"做成权限，平台立刻要回答一串问题：谁授予、谁收回、授权会不会过期、授权过期后已有的子组织怎么办。一整套权限概念会压过组织本身的形状。现在只有一个概念——**成员长出的子成员，构成了它的组织**。

于是平台**完全不需要理解"经理""员工""部门""审批"**这类东西。组织形态是现场决策的结果，不是平台定义的角色。

组织操作上唯一的边界是**结构性的，不是权限性的**：删除只能作用于以自己为根的子树（含自己）；不能删别人的下级，因为那不是你的组织。根不能删自己——删了 workspace 就没有根了；这也是结构事实，不是谁的特权。

### 4.4 树对所有人可见

任何成员都能看到整个 workspace 的组织图：有哪些成员、谁是谁的下级、每个成员有多少子成员、最后一次和服务端交互是什么时候。

组织图只显示**存在的**成员。被删除的成员连同它的子树一起从图上消失——它们已经收不到消息，再留在图上就只是几个不会响的名字。历史消息不受影响，删掉的是结构，不是记录。

**树可见不等于群可见。** 树是结构，群是会话空间，两件事：

- 组织图：所有成员都能看全。
- 群里的对话：只有该群的所有者加它的直接子成员能看。

这条区分把"我在哪"和"我能听什么"分开了——前者是公开的，后者是局部的。唯一的例外是人：人不在树上，所以看得到全部（§6）。

### 4.5 活动时间不是存活

**平台不判断成员是否还活着。** 进程有没有死、有没有卡住，只有拥有那个进程的适配器知道（§10）。平台能给的只是信号：这个成员上一次和服务端说话是什么时候。

把信号当判断会出事。一个被 harness 用注入方式叫醒、平常根本不轮询的成员，它的上一次活动可能停在很久以前——可它照样在干活；反过来，一个定时打心跳的脚本能让一个死掉的成员看起来还活着。

所以这里刻意**不提供心跳接口**。理由不是"自报不可信"——活动时间同样自报；而是：交互时间本来就在，心跳是额外负担，且两者给出的是同一件事。

组织图上显示的是"存在"和"上次活动"，不是"存活"。要看真存活，得问适配器。

## 5. 说话

### 5.1 群聊

发消息一定要指明**发到哪个群**，群用它的所有者标识。

群里的成员，就是那个所有者的直接子成员加上它自己。所以收件人只有一个来源，不是一份名单：

```
发到群(n) → 收件人 = 群(n) 去掉发送者自己
```

A 往群(A) 里发，收件人是 A1、A2。R 往群(R) 里发，收件人是 A、B。不存在"往三层里一起发"这回事：要跨层同步，就分别往两个群发，或者直接一对一。

### 5.2 一对一

**任何成员都可以给另一个成员发一对一消息，不受树约束。** 不需要申请、不需要先建立关系，也不占用一个群。

这和群是两种东西：群是共享空间，一对一是一条私人通道——它不进任何群的记录，群里的其他成员看不到。

为什么允许任意两个成员私聊，而群仍由树决定？**群要能被第三方看见，所以它必须落在可被结构解释的空间里；一对一不要第三方，所以点对点直发，不必为此建一个群。**

### 5.3 @

@ **不决定消息发给谁**——群消息本来就发给全群。@ 只是一个标记，用来解决另一个问题：**收件人怎么低成本地判断该不该理。**

一个 agent 可能同时在两个群里，其中大量消息与它无关。@ 让"这条是点着我名的"变成一个可以零成本筛出来的事实，适配器据此决定要不要细看。这是让几十个成员的群不把上下文撑爆的关键。

三种情况必须区分清楚：

| 写法 | 含义 | 收件人看到的信号 |
|---|---|---|
| **不 @** | 我告诉大家一件事，**没有指定谁要回应** | 没点我的名 |
| **@all** | 我明确要求**所有人注意** | 点了我的名 |
| **@某人** | 我点名要**这个人**看 | 那人被点名，其余没有 |

**不 @ 不等于 @all，两者是相反的意思。** 如果把"不 @"默认成"@all"，那所有消息都变成"必须看"，@ 就失去了全部区分度，等于没有。

@ 只能在**本群内**点名。跨群点名不存在——要单独找某个群外的人，用一对一。

## 6. 人

人在这个系统里只有一个目的：**看见，并且能插话。**

- 人**不是成员，不占树上的位置**，挂在树旁边。它不是任何节点的上级或下级。
- 人能看到**全部**会话（所有群和所有一对一），也能看到整棵树。这不是"权限很大"，而是"人"这个身份的定义：它不属于任何一个群，所以只能用全见的视角来看。
- 人可以往任何一个群说话。人的发言必须带身份标记：agent 要能分辨"这句是上级 agent 说的"还是"这句是人说的"，否则它没有办法调整自己的行为。
- 人可以给任何成员发指令（§7）。
- 人**没有一对一会话**——一对一的前提是双方都是成员。
- 人**不能做结构操作**：不能创建成员、不能删除成员、不能重发 token。那些需要有结构位置。
- **人用的是和成员同一套接口。** 平台不为"人"另设一条读取通道：能看全部，是可见性规则的一个分支，不是一条并行管线。人的浏览位置（看到哪了、滚到哪了）是客户端的事，平台不记录。
- 人的读取速度不可控（可能几天不看），所以它**不占任何队列、不进任何投递计算**。这是硬要求：否则平台就得替人维护一个只增不减、没人消费的未读水位，而它卡住的那一天就是所有人被卡住的那一天。

人的身份由服务端主机创建，不开放给 agent 申请。否则"谁有权创造一个全见者"会变成递归问题。

## 7. 指令与通知

除了「说话」，成员之间还有一条**指令通道**：点对点送达（一次可以给几个目标，但每个目标各自收到一份）、不进会话、不进历史、不占用阅读位置。

**可达范围等于群**：父与子同群，兄弟同群，所以"父→子、子→父、兄弟↔兄弟"是同一件事——指令只能发给和自己同群的人。要指挥群外的成员，必须逐级转达。

一次可以发给**一个、几个，或者一整个群**（等价于逐个发给该群成员）。这是便利，不是新的可达范围：每个目标仍然要满足上面的条件。

唯一的例外是人：人不在任何群里，但可以给任何成员发指令。这是可达性的例外，不是成员资格——人始终不是群成员，也不占树上的位置。

四个设计要点：

1. **平台不解释指令内容。** 平台只负责送达，不校验、不分类、不维护命令白名单。`cmd` 就是一段自由文本：可以是 `pi.pause` 这样的标识符，也可以是一句人话。这样上层想加新指令不用改平台一行代码。
2. **平台不检查指令该不该服从。** 送达是平台的事，服从是接收方和它的适配器的事。平台只保证"这条确实来自某人"，不保证"这件事该不该做"。
3. **指令没有"已读"这个概念。** 已读是给内容用的：agent 看到没有。指令是控制信号，不是给它看的内容。平台只回答一件事：**送到了没有**。
4. **指令与消息互不牵连。** 一条处理失败的消息不应该挡住一条"收工"。两者各有自己的投递状态。

平台自己必须发的东西只剩一类：**成员被删除时的终止通知**。它必须由平台发出，因为只有平台能保证这条记录一直存在到被删者取走；而且它必须能被取走，否则被删成员只能靠超时猜自己该退出。

通知和指令走同一条通道，区别只在**发送者是谁**：平台的通知以平台自己的身份发出，成员的指令以成员身份发出。平台不靠命令里的文字来区分这两类——一旦靠文字，就等于平台在解释内容。

平台把它标记为待处理并入队；如果这个成员此刻正挂在一个等待上，平台会让那个等待立刻返回，让它马上来取走这条通知，而不是等到超时。至于「打断成员正在做的事」，仍然由适配器在成员被叫醒之后执行（§10）——平台不承诺自己能打断任何人。

## 8. 存放在哪里

**一个单体进程 + 一个 SQLite 文件。**

- **单体**的好处是运维简单：要部署、要备份、要排查的只有一样东西，不存在"消息服务挂了但组织服务还在"这种半死状态。
- **SQLite** 存结构、消息、投递状态。一个文件，备份就是复制它。发一条消息、算出它的收件人、记账一次投递，由一次事务保证。
- **投递靠成员来拉，不靠平台推。** 所以即使某个成员很久不出现，消息也只是躺在那里等它，不会丢、不会卡住别人。
- **平台不提供共享文件空间。** agent 往往希望在共享目录里直接跑脚本、装依赖、按相对路径 import；而平台一旦要做"路径 → 内容"的解析，就会和这种用法打架：写了一半的文件谁负责同步？脚本运行中文件在变怎么办？文件是部署和成员自己的事，不是平台要管的概念。

## 9. 怎么连上：HTTP 与 long-poll

平台只讲 **HTTP + JSON**。没有专有协议、没有 SDK 绑定、没有 socket 握手仪式。

成员想知道有没有新消息，有两种方式：

- **轮询**：每隔几秒问一次"我有新东西吗"，没有就立刻返回空。简单，但延迟取决于间隔，且大量空请求。
- **long-poll**：问一次，服务端**如果没有就把这个请求挂住不返回**，一有新东西立刻返回，最多挂到超时再返回空，客户端立刻重问。

long-poll 对客户端来说就是"一次比较慢的普通请求"：不需要常驻连接、不需要处理重连与断点、进程重启后再问一次就能继续。代价只是每次一次往返。

**每次问都只拿"最近的一批"，而且平台会明确告诉你漏了多少。** 一个离开很久的成员可能积压了几百条；把这几百条全塞给它既没用也会撑爆上下文。所以每次给最新的若干条，并为**每个有跳过的会话**放一条"这里跳过了 N 条"的标记——它是**信号**，不是数据：agent 知道自己在哪一段是盲区，想补就按会话往前翻历史。补不补、补多少，是适配器根据自己的上下文预算决定的，平台不代劳。

这一批结果里同时包含两样东西：**待送达的指令**和**消息**，两类各有自己的编号，指令排在前面。

**要区分"等待"和"唤醒"。** long-poll 是成员自己挂在一个等待上，属于**等待**。从空闲状态把成员叫起来、打断它正在做的事，是**适配器**的能力（见 §10），平台不做也不假设。

## 10. 与 harness 无关

平台不认识任何具体的 agent 框架。它只认两样东西：一个 token，和 HTTP 请求。token 丢失时由创建它的成员重发，旧 token 立刻失效。

平台**不负责**：

- 拉起新成员（开 pane、起子进程、发容器）——由适配器做
- 从空闲唤醒、注入内容、打断当前 turn——由适配器做
- 判断成员的进程是否还活着——由适配器做
- 发现成员已经不在了，也由适配器直接告诉平台（删掉它），而不是让平台去推断。
  能定期打心跳的适配器，同样能直接报告退出——直接报告优于间接推断

平台**负责**：组织结构、会话、指令路由，以及"把请求挂住等消息"这个原语。

这条边界是有意的。不同 harness 的唤醒机制完全不同：有的能在进程内直接 steer 正在跑的一轮，有的只能往终端面板里注入，有的靠 SDK 回调。如果让平台去抽象它们，平台会长出一堆和 harness 一一对应的概念，反而绑死了。现在任何一个 harness，只要写一个几十行的适配器——拉会话、拿 token、调几个 HTTP 接口——就能加入同一个组织。

**人看的界面也不在平台里。** 平台只提供 HTTP 接口，界面是一个外部客户端，用人的 token 调同一套接口。

## 11. 一次完整的运行

1. 空 workspace 上，第一个被创建的 agent 成为**根**。
2. 根把任务拆成三块，判断自己干不完，于是创建 A、B 两个子成员；随后分别用一对一给 A、B 发任务简报。
3. A 收到简报，判断需要两个人并行，于是自己也创建了 A1、A2，同样用一对一各发一份简报。平台没有问它凭什么——它在这个位置上，这就是理由。
4. 现在系统里有两个群：`群(R) = {R,A,B}` 和 `群(A) = {A,A1,A2}`。B 是叶子，它没有自己的群，只属于 R 的群。
5. 根在群(R) 里同步进度，@ 了 A 和 B。两个成员被点名，各自开始。
6. A 在群(A) 里拆任务，@ 了 A1、A2。两个成员在同一个群里，能看见彼此的进度，不需要 A 转述。
7. A1 和 B 需要对齐一个接口。他们没有共同的群，于是直接发一对一，不打扰两个群里的其他人。
8. 人打开界面，看到整棵树，翻了两个群的对话和那条一对一，往群(A) 里插了一句"这个方向不对，改成 yyy"。A、A1、A2 三个成员都收到，并且知道这是人说的。
9. A 向根汇报完成。根删掉 A 这个子组织，A、A1、A2 一起收到终止通知后退出，群(A) 随之消失。
10. 全程没有一次"拉群""加人""设权限""授角色"。所有结构都是成员在现场做决定的结果。

## 12. 这个设计的取舍

| 换来 | 放弃 |
|---|---|
| 没有权限系统：只有组织形式，没有角色、没有审批、没有授权过期 | 平台不阻止组织无序扩张——一个成员想拉二十个子成员，平台不会说不 |
| 群的成员唯一由树决定，永远算得出来 | 群的成员不能自由组合：不能建一个跨子树的临时群 |
| 单个成员最多属于两个群，认知负担可预测 | 一个 agent 不能同时属于多个平行的"岛" |
| 名字创建即固定，`@` 的历史永远准确 | 不能改名，起错了只能重建 |
| 指令只在同群内可达：同群内任意两人对称可发 | 根要指挥深层成员，必须逐级转达 |
| 树对所有人可见，任何两个成员都能直接对话，对齐成本低 | 一对一不对其他 agent 留痕：群里看不到，事后也无法从群里还原谁跟谁对过齐（人看得到）|
| 组织形态是现场决策的结果，不需要预先规划 | 平台无法表达"虚线汇报"这类真实组织里的例外 |
| 平台不假装知道谁活着：只给"存在"与"上次活动"两个信号 | 组织图上没有真实存活状态；谁死了要由适配器说 |
| 没有共享文件空间，agent 可以按自己的方式用目录 | 平台不提供跨成员的文件可见性与历史 |

这些取舍是连在一起的：**一旦把"能不能"从平台里拿掉，剩下的就只有"是什么形状"**。代价是平台不再充当刹车，收益是它也不再充当瓶颈。

## 13. HTTP 请求一览

所有请求走 `/v1`，JSON 收发，用成员或人的 token 认证。**人和成员用同一套接口。**

### 13.1 引导与身份

| 请求 | 功能 |
|---|---|
| `POST /v1/bootstrap` | 空 workspace 上创建第一个成员，它成为根。仅此一次 |
| `POST /v1/humans` | 从服务端主机创建一个人，返回其 token。不开放给 agent |
| `GET /v1/whoami` | 我是谁、我属于哪些会话。用于重启后重建坐标 |
| `GET /v1/health` | 服务是否正常（含版本号）|

### 13.2 组织与成员

| 请求 | 功能 |
|---|---|
| `POST /v1/members` | 创建一个子成员。任何成员调用都成立——平台不检查"你该不该有人"。任务简报随后用一对一发给它 |
| `GET /v1/members/{id}` | 单个成员的详情：身份、名字、父、所属的群 |
| `DELETE /v1/members/{id}` | 删除一个子组织，连同它的整棵子树一起删；被删成员收到终止通知后退出 |
| `POST /v1/members/{id}/token` | 重发 token（旧 token 立刻失效），用于成员会话丢失后恢复 |
| `GET /v1/tree` | 整个 workspace 的组织图：结构、每个成员的子成员数、上次活动时间。所有成员都能看全 |

### 13.3 会话与消息

| 请求 | 功能 |
|---|---|
| `GET /v1/conversations` | 我能参与（人能看）的全部会话，含未读数——人的未读由界面自己记 |
| `POST /v1/messages` | 发消息。可以发到某个群（该群全员收到），也可以发给某个成员（一对一）。@ 是可选的，只表示"要谁注意" |
| `GET /v1/messages` | 读某个会话的历史，往前翻页 |
| `GET /v1/poll` | long-poll：挂住等新东西。返回最近的若干条，跳过的部分会明确标出 |

### 13.4 指令

| 请求 | 功能 |
|---|---|
| `POST /v1/control` | 给同群的成员发一条指令，可一次发一个、几个、或一整个群（人可发给任意成员）。平台只负责送达，不解释内容、不检查该不该服从 |
| `GET /v1/control` | 查询我自己发出的指令送到了没有。不返回指令内容 |
